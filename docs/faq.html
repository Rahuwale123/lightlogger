Frequently asked questions

Port 4356 is already in use — what happens?

lightlogger auto-increments to the next free port (4357, 4358, …) and prints the actual bound URL to stdout. You never need to configure this yourself — it just works, and you always know the real URL because it's printed:

lightlogger UI → http://127.0.0.1:4357

Mechanically, start() tries to bind your requested port; if binding raises OSError (the port is busy), it retries with port + 1, and keeps incrementing until a bind succeeds. If you need a specific port and want a hard failure instead, pick one you know is free and don't rely on the fallback.

Why don't my lightlogger.info(...) or logging.info(...) calls show up?

start(capture_logging=True) (the default) attaches a handler to the root logger, but Python's root logger defaults to level WARNING — and lightlogger deliberately never forces that level open, since doing so would also unmute your app's other existing handlers, which is more disruptive than "zero code changes" is meant to be.

Call logging.basicConfig(level=logging.INFO) yourself if you want .debug()/.info() calls to appear too; .warning() and above always show up out of the box, with no configuration needed.

This only affects logs routed through the standard logging module. Calls to lightlogger.info()/lightlogger.debug() directly always appear — they go straight into lightlogger's own buffer, not through the root logger's level filter.

Can I run this in production, or expose it beyond my machine?

No, not as designed. lightlogger binds to 127.0.0.1 only by default, so nothing is reachable outside your machine unless you explicitly pass host="0.0.0.0" — which prints a loud warning when you do, precisely because it's an unusual, deliberate choice rather than a default.

It's a local development tool, not a production observability platform: don't run it against a public-facing process, and don't leave it running longer than your debugging session needs. See SECURITY.md for the full threat model.

Will lightlogger run my app out of memory?

No — logs live in a fixed-size ring buffer (collections.deque(maxlen=max_logs), default 5000). Once it's full, the oldest record is dropped for every new one that arrives, so memory use is bounded no matter how long your app runs or how much it logs.

Raise or lower the bound with the max_logs parameter:

lightlogger.start(max_logs=20000)  # keep more history, still bounded
